# NowUs 首发平台与登录方案

日期：2026-09-29。

状态：用户确认先做 Android，iOS 后续，登录采用邮箱验证码。Android 已选择 Kotlin + Jetpack Compose；本地后端已选择自托管 FastAPI + PostgreSQL + Mailpit。云服务商、部署地域、域名和真实 SMTP 仍未提供或验证。

## 已确认的人群

第一批用户以“中国大陆一方 + 海外一方”的跨时区情侣为主，学生与上班族、作息相对固定。原型已试用，接下来解决真实账号、双方配对与同步。

## 已确认的选择

| 决策 | 确认方案 | 取舍 |
| --- | --- | --- |
| 开发与首轮试用平台 | Android 可安装 App 优先，iOS 后续 | 先验证 Android 安装、交互、邀请接续与账号同步，再安排 iOS。框架选择仍需考虑后续双端复用。 |
| 登录方式 | 邮箱 + 6 位一次性验证码 | 双方使用同一种方式，不要求同一社交账号体系或手机号地区；需要验证邮件送达。 |
| 账号入口 | 注册与登录合并 | 用户无需先判断是否已有账号；首次验证成功后进入自己的资料设置，已有账号恢复原资料与配对。 |
| 邀请方式 | 用户主动分享链接；App 内提供输入邀请码入口 | 已安装用户从链接进入邀请；未安装用户可安装后用邀请码继续。不能假设安装后会自动恢复链接上下文。 |
| 首版语言 | 沿用现有中文体验 | 后续按真实用户需要增加英文。 |

用户选择了原生 App 方向，原有手机网页原型保留为体验参考。首版仍聚焦作息、共同窗口、短留言与分享控制，暂不加入小组件、系统通知或通话。邮箱验证码登录保持双端统一入口。

## 安装与试用方案

先进行 Android 小规模内测，提供签名的内测 APK；iOS 阶段再安排 TestFlight。正式应用商店发布渠道在发行阶段确定，国内 Android 用户的安装入口需要单独落实。

Android 本地 debug APK 已可构建并曾在一台 Android 设备安装；debug 包不是发布签名包。内测前仍需准备签名、安装指引和至少两台验收设备；iOS 签名、开发者账号和设备在后续阶段准备。

## 登录和邀请体验

1. 未登录时可以看产品说明及明确标识的示例，不展示真实伴侣信息。
2. 在 App 输入邮箱，请求验证码，再回 App 输入验证码完成验证；首版不依赖点击邮件登录链接。
3. 新用户进入已有的昵称／城市／节奏流程；已有用户恢复自己的资料与配对。
4. 有效登录期间日常打开尽量无需再次验证；主动退出或会话失效后重新登录。
5. App 重启后恢复有效会话；重装或换设备需要登录时，用同一邮箱恢复原账号，不新建重复配对。两端各自管理会话，App 返回前台时核对有效状态与数据。
6. 已安装 App 时，`nowus://invite/{CODE}` 邀请链接打开 App，显示邀请人昵称、城市与共享范围；链接上下文在登录前后保留，登录后预览，明确接受才配对。未安装时仍需使用手动邀请码继续；目前没有网页落地页或 Android App Link 域名配置。邀请链接本身不作为登录凭证。
7. 邮箱只用于自己的账号，不向伴侣显示；登录验证码与配对邀请代码各有独立用途和有效期。

建议产品参数：验证码 10 分钟有效、60 秒后可重发；验证码一次使用，错误输入、过期、发送失败和频率限制分别反馈。发送和验证限制由服务端执行，用户输入不因错误丢失。具体认证服务还需确认能支持这些参数；它们不是任何供应商的默认值。

首版仅提供邮箱验证码入口，暂不增加密码、短信、微信、Google、Apple 登录。以后新增方式时，绑定到既有账号，不因入口变化创建第二个身份。

## 针对大陆与海外双方的发布验收

| 项目 | 发布前必须验证 |
| --- | --- |
| 国内外访问 | 用真实大陆网络和首批海外用户所在地网络检查 App 登录、邀请与同步，以及邀请落地页；安装成功不等于接口可用。 |
| 邮件送达 | 用测试账号分别检查 QQ、163、Gmail、Outlook；记录到达时间、收件箱／垃圾箱位置及失败反馈。邮箱名单可按试用者实际邮箱增补。测试由产品方或自愿参与者自行请求验证码，不自动给他人发邮件。 |
| 跨手机使用 | Android 第一轮用两台设备、两个账号验证安装、登录、配对和同步，覆盖实际国内 Android 机型；iOS 阶段再做 iPhone／Android 交叉验证。 |
| 分享入口 | 在试用者常用通信工具检查已安装／未安装、App 冷启动／已打开、登录／未登录四类条件；无法直接打开 App 时可用邀请码接续。 |
| 会话恢复 | App 重启、返回前台、退出、重装和换设备分别验证；同一邮箱恢复同一个账号，邀请与配对不重复。 |
| 失败恢复 | 邮件未到可以重发或更换输入邮箱；登录错误／过期可重试；请求成功只表示请求已受理，不能声称已送达收件箱。 |

这些是验收任务，不代表已经验证上述网络或邮箱可用。网页原型仍只有本地模拟配对；Android 工程现在连接本地 FastAPI/PostgreSQL 服务，开发邮箱进入 Mailpit。生产部署与邮件送达仍待真实资源和测量。

## 技术选择与部署边界

本地 Android 客户端采用 Kotlin + Jetpack Compose，并保留既有 Kotlin 时区与共同窗口逻辑。服务端采用 FastAPI + PostgreSQL，邮件在开发环境进入 Mailpit；生产 SMTP 从环境变量接入。方案比较、权限模型、迁移和运行说明见 [真实账号同步架构选择](2026-09-30-nowus-real-sync-architecture.md)。

本地双账号闭环通过 API 客户端验收：邮箱 OTP → 邀请预览与明确接受 → 双方作息／留言同步 → C 账号拒绝访问 → 暂停／解除撤销共享。它只验证本地功能和 SMTP sink。真实部署地域必须结合大陆与海外真实网络测量，不根据“全球可用”宣传推定大陆可达性；服务采购、域名与生产邮件账号仍待提供。

## 核对依据

- [TestFlight](https://developer.apple.com/testflight/)：iOS 内测试用分发方案。
- [Expo EAS Build](https://docs.expo.dev/build/introduction/)：支持 iOS／Android 云端构建，Android 内测可生成 APK；仅作为技术候选资料，不表示已选用或已配置。
- [Flutter iOS 开发环境](https://docs.flutter.dev/platform-integration/ios/setup)：本地 iOS 构建与测试需要 Xcode 环境。
- [邮箱验证码机制](https://supabase.com/docs/guides/auth/auth-email-passwordless)：区分邮箱 OTP 与登录链接；可配置有效期。引用仅证明机制可用，不表示已选择 Supabase。
- [生产邮件配置](https://supabase.com/docs/guides/auth/auth-smtp)：若后续选择 Supabase，必须另行配置生产邮件服务，不能依赖其受限制的默认测试 SMTP。
