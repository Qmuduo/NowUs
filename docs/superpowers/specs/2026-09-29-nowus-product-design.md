# NowUs 产品设计：跨时区情侣的日常节奏与陪伴

日期：2026-09-29

状态：根据本次头脑风暴中用户确认的方向整理的产品设计基线。

范围：产品定位、核心场景、MVP、信息架构、交互原则与验证方向。本文不包含技术选型、系统架构或开发计划，不构成开始技术实现的授权。

## 1. 已确认的选择

| 决策 | 已确认方向 |
|---|---|
| 第一批用户 | 作息相对固定的跨时区学生和上班族情侣 |
| 产品主线 | 用较少的维护，看懂彼此的一天 |
| 首页重心 | 优先「看见你的生活」，共同联系时间紧随其后 |
| 第一版陪伴方式 | 一条短留言 |
| 产品边界 | 保留现有通信工具，不把第一版扩展成完整聊天或情侣功能合集 |

## 2. 核心问题与定位

### 核心问题

时差带来三种成本：换算当地时间和日期的认知成本、协调联系机会的沟通成本，以及缺少生活背景时的关系不确定感。

产品通过双方时间、规律作息与主动分享的信息，为用户提供生活背景；通过共同窗口帮助安排联系；通过短留言支持错开时间后的关心。

### 一句话定位

帮助跨时区情侣看懂彼此的生活节奏，并找到舒服的相处机会。

### 用户打开产品时应得到的答案

1. 你的一天进行到哪里了？
2. 我们什么时候方便联系？
3. 我想给你留点什么？

「共同经历同一天」指理解和参与彼此的日常，不意味着双方处于同一个日历日期。界面始终保留双方真实的当地日期。

## 3. 设计原则

1. 通常作息、当前实际状态、联系意愿是不同信息，不能互相等同。
2. 按作息推测的信息必须说明来源，不能显示为实时事实。
3. 空白安排属于未知，不能自动认定为空闲。
4. 休息不代表愿意通话，有空不代表有回复义务。
5. 分享以主动设置为基础，不依赖定位、在线监测或自动活动识别。
6. 日常无需持续报备，重点降低首次设置和例外调整的负担。
7. 联系机会与陪伴表达并存；没有共同窗口时，产品仍然有价值。
8. 不用已读、连续打卡、回复速度或亲密度评分制造回应压力。

## 4. 核心场景

| 场景 | 产品帮助 | 信息边界 |
|---|---|---|
| 临时想联系 | 看对方当地时间、生活阶段、联系偏好 | 未经主动更新的状态只是作息推测 |
| 暂时没有回复 | 提供睡眠、上课、工作等生活背景 | 不解释未回复原因，不判断伴侣态度 |
| 安排通话或视频 | 展示共同窗口、时长和双时区时间 | 窗口建议不等于双方确认的约定 |
| 一方起床、一方睡觉 | 留下一条关心 | 不要求同时在线或立即回应 |
| 今天加班、考试或外出 | 修改当天安排或临时状态 | 例外有明确作用范围，不永久改变通常作息 |
| 今天没有交集 | 清楚显示结果，继续允许留言 | 不建议以牺牲睡眠换取联系 |

## 5. MVP 功能范围

### 5.1 双方配对与当地时间

- 设置昵称、头像和城市，通过邀请完成双方配对。
- 同时显示双方当地日期与时间。
- 用自然语言说明对方比自己快或慢多少小时；时间差可包含分钟。
- 城市由用户选择，不要求持续定位。
- 旅行或季节性时区变化后，双方时间、时差和共同窗口仍应准确；当地作息以当地时间理解。
- 伴侣尚未加入时，允许先建立自己的作息，不虚构对方状态。

### 5.2 通常作息

- 提供工作日和休息日两套模板，学生模板为默认；用户也可选择上班族模板。
- 每段时段可滚动改时、改名、添加或删除，包含睡眠、早餐、通勤、上课／工作、午餐、午休、晚餐与个人时间。
- 城市只改变可编辑的建议起点；用户没有确认的空档仍显示“未安排”，不推断为实时活动。
- 活动与联系偏好分开表达，活动提供的默认联系偏好必须可修改。
- 第一版使用简单的「愿意联系／暂不方便」，没有设置的时间标为未知。
- 作息是规律背景，不是对实际活动的承诺或证明。

### 5.3 今天的例外与临时状态

- 支持今天加班、提前休息等当天变化。
- 支持「接下来一小时有空」「暂时不方便」等快速设置。
- 临时设置有明确结束时间，到期回到当时适用的安排。
- 展示优先级：有效的主动临时设置 → 今天的安排 → 通常作息 → 未知。
- 临时活动更新若未表达联系意愿，不得仅凭活动名称判断其愿意聊天。
- 自己的作息由自己维护，不能替伴侣直接改写其状态或联系意愿。

### 5.4 双方对照时间轴

- 同一位置表示同一个真实时刻，分别显示双方对应的当地时间与活动。
- 手机端采用纵向阅读方向，双方并列，便于对照同一时刻。
- 首页围绕现在展示附近时段，完整一天进入详情查看。
- 当天详情明确以查看者的当地日期为基准，保留另一方真实日期。
- 双方跨午夜的位置分别标注日期；跨午夜睡眠保持连续表达。
- 共同窗口横跨双方区域高亮，颜色同时配合文字和图标。
- 短活动允许展开查看；提供回到现在的入口。

### 5.5 共同可联系窗口

- 根据双方明确设置的可联系时间及有效例外，展示交集、时长和双方当地日期时间。
- 当前有交集时，优先展示当前窗口；否则展示接下来的窗口。
- 区分按作息估计的窗口和主动更新支持的窗口，不把任一种视为预约。
- 可给自己设置提醒，不默认替对方开启提醒。
- 对方临时设置不方便时，相应时段不继续推荐联系。
- 双方资料不足时，说明尚不能推荐；未知时间不能作为共同空闲。
- 没有交集时说明结果，保留留言入口。
- 第一版不包含双方预约确认、改期或完整通话功能。

### 5.6 当前短留言

- 每个人有一条当前留言，首页可查看双方的留言。
- 新留言替换自己上一条；发布入口明确说明替换规则。
- 支持简短文字，可以修改或删除自己的留言。
- 留言不自动消失，直到作者删除或替换，避免对方醒来时已错过。
- 展示发送时间，可展开查看双方当地时间。
- 留言不强制绑定作息活动，普通生活表达同样适用。
- 第一版不保留聊天线程或历史留言列表，不设置已读与回应任务。
- 默认打开 App 时查看。留言通知由接收方主动选择，不根据推测的起床时间自动发送通知。

## 6. 首页信息架构

首页以「看见彼此的生活」为核心，工具信息紧随生活信息。

| 层级 | 内容 | 作用 |
|---|---|---|
| 第一层 | 双方头像、城市、日期、时间与昼夜氛围 | 建立此刻的时间关系 |
| 第二层 | 双方当前生活阶段、来源、下一次阶段变化；对方为视觉重点 | 理解对方的一天，自己可随手调整状态 |
| 第三层 | 当前或下一段共同窗口、双时区时间、时长 | 支持联系判断与自己的提醒 |
| 第四层 | 双方当前短留言与写留言入口 | 在时间错开时仍能表达关心 |
| 展开入口 | 完整对照时间轴 | 理解双方的一天怎样交错 |

日期不能隐藏。用「对方那里还是昨天／已经是明天」辅助解释，但始终显示明确日期。

生活氛围可以通过柔和的早晨、午后或夜晚表达，不能削弱时间、状态来源与共同窗口的可读性。第一版不要求精确的日出日落或天气效果。

文案示例：

- 「对方这个时段通常在上课。」同一区域标注「按通常作息」，避免呈现成实时事实。
- 「对方设置了『今天在图书馆』，到当地时间 18:00。」
- 「按双方作息，下一段可联系时间在 2 小时后。」
- 「按目前的安排，今天没有共同可联系时间。」

## 7. 产品页面与使用路径

| 页面 | 内容 |
|---|---|
| 此刻：首页 | 双方时间、当前阶段及来源、共同窗口、短留言 |
| 我们的一天 | 完整对照时间轴、日期切换、窗口详情 |
| 我的节奏 | 通常作息、今天的例外、联系偏好 |
| 设置 | 配对、城市、提醒、分享范围、暂停分享、解除配对 |

首次使用：选择城市 → 填作息骨架 → 标记愿意联系的时间 → 邀请伴侣 → 双方对照。

日常使用：理解此刻 → 查看共同窗口 → 用现有通信工具联系或留下一句话 → 有变化时快速调整。

## 8. 特殊情况与分享边界

- 对方未加入或未填写作息：显示真实缺失状态，不生成假日程。
- 对方长期未主动更新：只能依据其仍适用的通常作息推测，不能把过期临时状态继续显示为当前状态。
- 双方当地日期不同：分别标注，不用统一日期掩盖差异。
- 临时设置到期：恢复适用安排；不存在安排时恢复未知。
- 暂停分享：说明信息当前不可用，不继续推测已暂停的信息。
- 分享范围可选择具体活动或仅忙闲，减少维护与披露负担。
- 解除配对后，双方不能继续查看对方的作息与留言。
- 通知由接收方选择，不能因为对方留言就自动产生回应义务。

## 9. 暂不纳入第一版

- 完整聊天、语音和视频通话。
- 复杂共享日历、待办、轮班和多变行程管理。
- 定位、在线监测、自动识别活动。
- AI 情感分析、未回复原因判断或回复预测。
- 相册、恋爱日记、游戏、虚拟宠物、纪念日合集。
- 连续打卡、亲密度分数、回复速度排名。
- 双方预约确认、改期流程与复杂联系类型偏好。
- 日历导入、桌面小组件、语音留言与定时投递。

筛选标准：功能是否直接帮助理解彼此、找到联系机会，或在错过时表达关心。

## 10. 差异化与陪伴感

普通时区工具解决时间查询与换算，共享日历组织具体事件，部分情侣产品通过问题与互动支持关系交流。这里的差异化假设是把这些需求连接到跨时区的生活节奏上：

看懂对方的一天 → 理解现在是否方便 → 找到共同时间 → 错过时仍能传递关心。

低维护成本、状态可信边界和低压力表达，是需要验证的体验优势；双时区显示本身并不足以构成差异化。

陪伴感由三种体验形成：生活阶段有温度的表达、对照时间轴中的彼此理解、具体而不要求回应的留言。第一版不靠互动数量堆积陪伴感。

## 11. 产品验证

### 需要验证的假设

1. 双方愿意完成简单设置，并偶尔维护例外。
2. 作息背景能帮助理解，用户能区分推测和主动分享。
3. 共同窗口实际帮助协调，且不会增加必须回应的压力。
4. 短留言能自然表达关心，不需要扩展成聊天才能成立。

### 建议验证方式

邀请少量目标情侣，先做首页和时间轴的理解测试，再进行一到两周的体验验证。观察双方是否愿意加入、是否正确理解日期与状态来源、窗口是否有用、作息是否容易失效，以及是否产生报备或回应压力。

验证以情侣双方为单位，关注双方持续参与、维护负担、窗口准确性、实际协调帮助与主观压力。打开次数和留言数量只是辅助信息，不作为独立成功标准。

体验目标：不必填写完整日历即可开始；几秒内理解对方时间和生活阶段；几步完成当天调整。具体时间和效果需通过用户测试确定，不预先宣称已达成。

## 12. 后续扩展顺序

1. 核心体验稳定后：桌面小组件、更多固定作息模板、未来几天窗口。
2. 联系协调需求明确后：双方确认预约、改期、文字／语音／视频偏好。
3. 陪伴需求明确后：生活照片、语音留言、双方约定的小仪式与共享回忆。
4. 特殊作息需求出现后：轮班、考试周、出差与临时城市。
5. 产品成熟后：自愿导入日历，以及异地家人等相邻人群。

每一阶段都先验证需求与维护成本，避免偏离跨时区情侣的日常节奏主线。

## 13. 当前阶段结束边界

本次已确认产品方向，并整理产品设计基线。后续讨论可以围绕首页视觉、时间轴理解测试、作息设置和短留言体验展开。技术方案、实施计划与编码仍不属于当前授权范围。
