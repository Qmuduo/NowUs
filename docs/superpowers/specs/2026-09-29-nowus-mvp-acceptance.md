# NowUs 正式 MVP：功能与验收标准

日期：2026-09-29。对象：作息相对固定、身处不同时区的学生与上班族情侣。

## 产品目标

用户打开首页后，能看懂对方当地是什么时候、通常在做什么，以及下一段双方愿意联系的时间；错开时可以留一句关心。通常安排不是实时行踪，联系偏好不构成回复承诺。

第一版的完整路径：登录 → 选择昵称与城市 → 设置自己的节奏 → 邀请伴侣 → 对方明确接受并填写自己的信息 → 查看共同首页与时间轴 → 调整临时状态或留一句话。

允许先进入个人首页，邀请稍后完成。等待配对时不生成对方的城市、时间、作息或留言。配对成功但对方尚未填作息时，可以显示其选择的城市和时间；活动与联系偏好仍然未知。

## 发布必需功能（P0）

| 功能 | 第一版范围 | 验收标准 |
| --- | --- | --- |
| 账号与会话 | 一种登录方式；恢复当前配对 | 两个独立账号在两台设备使用；重新登录恢复自己的设置；未配对账号不能读取他人的作息和留言。具体登录方式待选定。 |
| 个人资料 | 昵称、手动选择城市／时区 | 昵称为空或超过 20 个字符时不能保存；作为纯文本显示；无须定位权限；修改城市后日期、时差、时间轴和共同窗口一起更新。 |
| 邀请与接受 | 一对一配对、24 小时有效邀请、撤销／重建 | 接收人看见邀请人及共享范围后明确接受；错误、过期、撤销、自己邀请自己、任一方已经配对时均不能新建配对；并发接受只允许一个接收人成功；重建使旧邀请失效。失败不会清空已有资料。 |
| 通常作息 | 工作日周一至周五／休息日周末；睡眠、上班／上课或无固定安排；一段联系偏好 | 双方各自填写自己的当地时间；支持跨午夜；拒绝睡眠与主要活动冲突；联系时间不得覆盖睡眠；允许与上班／上课重合，但明确说明。未细分时间保持“未细分安排”，不猜测吃饭／休息。 |
| 联系偏好 | 独立于日常活动；允许暂不设置 | 未设置为未知，不能计算为愿意联系；设置范围之外不推荐联系；有活动安排仍可单独标记愿意联系，界面不改写成“有空”。 |
| 当前状态 | 愿意联系／暂不方便；30 分钟、1 小时、3 小时；主动恢复 | 临时设置优先于通常作息，在持续时间内影响联系推荐；到期自动恢复；双方设备刷新后看见一致状态、来源及到期时间；不记录在线时长。 |
| 双方时间 | 当地日期、时间、星期、时差方向 | 同一个时刻对应正确的两份当地时间；覆盖跨日、夏令时切换、半小时／45 分钟时差；时差随日期变化，不能固定写死；没有对方城市时不显示占位城市的真实时钟。 |
| 对照时间轴 | 默认附近几小时、可展开我的当地一天；双列连续活动 | 同一高度对应同一时刻；各人的活动不因另一方活动变化而被无意义切碎；双方日期清楚，跨午夜标注；点活动看到来源与独立联系偏好。切换日期后的过去内容明确是按当前模板回看，不当作真实历史。 |
| 共同联系窗口 | 当前或下一段；未来七天；双方当地起止日期与时间 | 只取双方明确愿意联系的交集，临时忙碌排除相应分钟；当天没有交集可显示未来窗口；“七天无交集”与“资料不足”分别展示；始终注明按偏好估计、尚未约定。 |
| 一条短留言 | 每人一条当前留言；最多 120 个字符；编辑、删除 | 普通文本／换行可显示；空白与超长拒绝保存；新留言替换自己的旧留言，不能覆盖对方留言；重新登录可恢复；删除后对方下一次成功获取数据时不再显示；不做已读、催回复、历史聊天。未配对时可以先保存自己的草稿，接受页说明配对后会共享当前留言。 |
| 分享控制 | 暂停／恢复分享、解除配对 | 暂停后对方不能继续获取当前共享数据，界面明确暂停，不解读成忙碌；解除后双方不能继续访问彼此数据，旧缓存不能恢复成仍在配对；自己的个人节奏保留，重新配对需双方再次同意。 |
| 同步与失败状态 | 两台设备的保存与读取；重试；过期数据标记 | 保存失败保留输入并显示重试，不宣称保存成功；离线／刷新失败明确提示最后更新时间；不能把旧状态包装成实时状态；第三个账号没有读取或修改权限。同步时效在技术方案确定后写成可量化的发布标准。 |

第一版不必同时支持学生与上班族的全部活动类型。优先验证睡眠、固定主要活动、联系偏好这三项是否足以让用户理解彼此。

## 验收场景

1. **从零配对**：A 填写自己的城市与节奏，B 在另一台设备接受并填写；A、B 都能看见正确身份与时间。B 未填节奏时 A 看见未知，无推荐窗口。
2. **邀请失败与竞态**：错误／过期／撤销／被使用的邀请各有明确反馈；B、C 同时接受同一邀请只能成功一次；任何失败都不改变已有配对。
3. **跨日期与季节**：选择北京／纽约跨午夜、伦敦／纽约夏令时不同时切换，以及带非整小时偏移的时区；用明确测试时刻核对当地日期和窗口边界。
4. **生活与联系独立**：A 主要活动为上班且明确标为愿意联系；首页显示通常上班及独立偏好。A 临时忙碌后交集立即按持续时间扣除，到期恢复。
5. **未知与无交集**：B 跳过联系偏好时显示资料不足；双方明确设置但七天不重合时显示无交集；均不能推荐虚构窗口。
6. **留言与权限**：A 更新／删除自己的留言，B 成功刷新后对应变化；C 不可读取；A 不能修改 B 的留言；暂停或解除后共享读取失效。
7. **恢复与失败**：重登恢复自己的资料与配对；保存失败不丢输入；断网后提示数据可能过期，恢复连接后重试，无重复配对或重复留言。

上线前至少完成两账号／两设备完整闭环，所有 P0 验收通过，无日期计算、配对越权或共享数据泄漏阻断问题。

## 本轮暂不包含

完整聊天、语音／视频通话、系统日历导入、自动定位、自动推测行踪、读回执、亲密分数、连续打卡、纪念日体系、日记相册、多段任意活动编辑、轮班作息、原生通知与小组件。原型里的提醒按钮仅演示反馈，不作为第一版发布要求。

## 原型与正式产品的边界

| 当前可评审原型 | 正式 MVP 尚需实现 |
| --- | --- |
| 选择有限城市、填写两套作息、本地保存 | 实际账号资料存储、完整城市／时区选择与双方数据同步 |
| 在同一浏览器模拟邀请、撤销、过期及接受 | 独立账号身份校验、唯一邀请、原子接受、访问控制 |
| 等待／配对／未填作息／示例已填写状态 | 对方真实填写并同步，不使用示例人物或示例作息 |
| 固定评审时刻与时间逻辑计算 | 当前真实时间推进、应用恢复与夏令时边界验证 |
| 本地短留言、演示提醒 | 每人当前留言同步、暂停／解除分享、失败恢复 |

邀请接收页中的“暂停分享／解除配对”是正式产品的共享约定，当前原型尚未提供这些操作。

## 开发前要确定的决策

- 首发载体：移动网页还是原生 App；以快速让真实情侣试用为主要取舍。
- 登录方式、部署区域与数据存储服务。当前没有作出技术选型。
- 同步频率、失败时展示规则与可量化时效。
- 暂停分享时是否只隐藏共享信息或保留旧留言；默认按本表隐藏共享信息。

## 小规模产品验证

找 3–5 对作息相对固定的跨时区情侣。先让他们独立完成资料与配对，再给“此刻能否联系”“下一次适合何时”“对方通常在做什么”的任务，观察是否把通常安排误认为实时行踪、把联系偏好误认为必须回复。记录填写耗时、困惑和是否愿意一周内持续使用；反馈用来决定是否需要增加活动粒度或通知，而不是提前增加功能。
